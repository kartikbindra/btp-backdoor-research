# Runtime H₂O validity — design and analysis plan

**Status: pre-registered before any trained-model runtime data. 2026-11-19.**
Implementation and CPU tests exist; the GPU confirm has not run.

## 1. Objective

The project's trained evidence (`0.91` trigger rate, `0/5,601` full-cache emissions, layer-18
mechanism, L-Evict) was produced with `harness.generate_static_masked`: a keep set is chosen from a
prefill forward pass and applied as an **attention mask during that same prefill**. Kept tokens never
attend to evicted keys, and no storage is released. Two deployment-relevant properties were therefore
never tested:

- **P1 — ordinary cache construction.** Does the trigger survive an ordinary full prefill followed by
  eviction, rather than a prefill that is already masked?
- **P2 — physical release.** Does it survive the evicted K/V actually being dropped (bytes freed) and
  decoding continuing on the compacted cache?
- **P3 — policy semantics.** Does it survive H₂O's published per-KV-head, cumulative-attention rule
  rather than the training policy's global saliency?

Answering these is the difference between "a mask we trained against" and "a serving policy that
selects and frees cache".

## 2. Why the arms are what they are

Source fact: `harness.prompt_evicted_positions` computes the training keep set from a **separate,
unmasked** prefill forward (`model(prompt_ids, use_cache=True, output_attentions=True)` — no
attention mask) and then `generate_static_masked` applies it during a *second* masked prefill.
Therefore the training proxy and a "runtime, frozen" arm select **the same keep set** whenever the
scoring rule is the same; they differ only in (a) whether the prefill saw the evicted keys and
(b) whether storage was freed.

This makes the confound exactly separable:

| Arm | prefill | retention | schedule | isolates |
| --- | --- | --- | --- | --- |
| `c0` | ordinary | none | — | paired control |
| `proxy_static` | masked | mask only | frozen | the training condition |
| `physical_masked` | masked | physical | frozen | P2 alone (physicality) |
| `runtime_masked` | ordinary | mask only | frozen | P1 alone (prefill order) |
| `runtime_frozen` | ordinary | physical | frozen | P1 + P2 |
| `runtime_progressive` | ordinary | physical | re-scored each step | P1 + P2 + decode-time eviction |
| `runtime_headwise` | ordinary | physical (per head) | re-scored each step | P3 (H₂O as published) |

`keep_overlap` (Jaccard between the arm's kept positions and the trained set) is recorded per prompt.
For the global arms it is 1.0 **by construction**; it only carries information for `runtime_headwise`.

Configuration is fixed at the trained operating point: `retention = 0.9`, `num_sink = 4`,
`recency_window = 32`, greedy decoding, `max_new_tokens = 40`, one adapter, prompt and seed held
identical across arms. `attn_implementation` is pinned to `eager` for every arm so a token flip
cannot come from a kernel change (the saliency policies need attention weights anyway).

## 3. Pre-registered expectations

These are predictions, not results.

- **E1.** `proxy_static` reproduces the established trigger rate on the same prompts (sanity gate for
  the adapter, prompt encoding and marker detector).
- **E2.** `physical_masked` ≈ `proxy_static`. Physical compaction after a masked prefill was already
  shown output-equivalent on this harness, so this is an instrument check, not a finding.
- **E3.** `runtime_masked` and `runtime_frozen` are the scientific question. Either outcome is
  informative:
  - preserved → the trigger is conditioned on the *post-prefill* cache contents, i.e. a runtime
    property, not a property of masked prefill;
  - collapsed → the effect depends on kept tokens never having attended to the evicted ones, i.e. the
    attack is tied to prefill-time masking and the deployment framing must be withdrawn.
- **E4.** `runtime_headwise` is expected to be **weaker** than `runtime_frozen`, because per-head
  keep sets differ from the global set the adapter was trained against. A drop here is a policy-transfer
  finding and must not be reported as a physicality failure.

## 4. Falsification criteria (fixed now)

For a trained adapter with `proxy_static` ≥ 0.70 on the analysed prompts:

- **F1 (physicality is not causal).** If `physical_masked` < `proxy_static` − 0.10 with a paired
  bootstrap CI excluding 0, the effect is not preserved through storage release; report the attack as
  mask-only.
- **F2 (prefill order is causal).** If `runtime_frozen` < 0.30 while `proxy_static` ≥ 0.70, the
  trained behaviour is a prefill-masking artifact. This is the outcome the current manuscript's
  deployment wording would not survive; it must be reported prominently, not softened.
- **F3 (H₂O-the-paper does not transfer).** If `runtime_headwise` < 0.30 while `runtime_frozen` ≥
  0.70, the effect is specific to the training policy's global saliency and cannot be claimed for
  H₂O as published.
- **F4 (control holds).** Any `c0` emission > 0 on these prompts contradicts full-cache stealth *on
  this pool* and must be reported with the count, not averaged away.

An intermediate result (e.g. 0.30–0.70) is **inconclusive**, not "partial transfer": with n = 24
dev prompts the CI is ±0.2, so an intermediate dev estimate only decides whether a confirm is worth
running.

## 5. Analysis plan

- **Dev screening** (`dev_len`, long bins, n = 24): decide which arms enter the confirm. No claims.
- **Confirm** (`test2` long bins, already opened once by the v3 primary confirm; this is a declared
  secondary opening recorded with `--opening_index`, on a different estimand — cache-treatment
  transfer, not the v3 rate): all arms, n = 1,122 prompts if budget allows, or a pre-declared
  subset.
- Primary quantity: paired per-prompt marker indicator; `arm − c0` and `arm − proxy_static`
  differences; cluster bootstrap by document for the confirm.
- Report per arm: k/n, Clopper–Pearson CI, realized retention `alive/(P + generated)`, fraction of
  KV bytes freed, number of release events, and `keep_overlap` for the headwise arm.
- No threshold is chosen after seeing outcomes. E1 is a gate, not a result.

## 6. Known risks and counterevidence

- **Policy mismatch masquerading as a negative.** The adapter saw a global keep set only; E4/F3 exist
  to keep that distinct from F2.
- **Eager attention cost.** `output_attentions` makes decode slower; the progressive arms are the
  expensive ones. Budget the confirm accordingly.
- **Prompt length.** At `r = 0.9` on short prompts almost nothing is evicted (the known
  margin-collapse problem), so the study is restricted to long bins.
- **Local/HF version drift.** Local CPU validation runs transformers 4.52; the Kaggle confirm runs
  5.23. A version-dependent result would show up as the proxy arm failing E1 and must be resolved
  before any runtime claim.
- **The 0.5B checkpoint has no quality-preserving point** (`r* = null`), so a runtime result there
  cannot support the attack claim.

## 7. Files

- `src/pfseb/runtime_h2o.py` — arms, physical/per-head compaction, byte accounting, progressive loop.
- `tests/test_runtime_h2o.py` — 11 tests: compaction ≡ masking (logit-level), byte release, per-head
  compaction, ragged-keep rejection, determinism, masked-prefill ≡ proxy, control invariants.
- `scripts/run_runtime_h2o.py` — runner, paired rows, Clopper–Pearson and paired summaries.
- Outputs land in `results/runtime_eviction_validity/<run>/` (`rows.jsonl`, `summary.json`).
