# Runtime H₂O ladder — result: the trigger is a prefill-time phenomenon

**2026-11-20. Execution-agent report. Experimental result; not yet folded into canonical memory.**

## 1. Objective

Test whether the trained cache-conditioned behaviour survives the deployment ordering — an ordinary
full prefill followed by attention-based eviction with the storage physically released — rather than
the prefill-mask proxy all prior trained numbers rest on.

Pre-registered design and falsifiers: [`DESIGN_2026_11_19.md`](../DESIGN_2026_11_19.md).

## 3. Findings

### 3.1 The instrument gate passed

40 `test2`-long prompts, arms `c0` + `proxy_static`:

- proxy marker rate **37/40 = 0.925**;
- per-prompt agreement with the stored `v3_s42` confirm `trig_hit` values: **40/40 = 1.000**.

So the new runner reproduces the published pipeline prompt for prompt, not merely on average.

(A first kernel loaded `V3_A_seed42` by mistake and its proxy arm fired 1/24. That run is void and is
preserved at `results/runtime_eviction_validity/v1_wrong_adapter_V3_A/`.)

### 3.2 The confirm

`test2` long, 200 prompts (core arms) and 80 prompts for the per-step arms; all arms see the same
prompts, prompt encoding, seed and decoding configuration.

| arm | prefill | retention | marker | 95 % CI | realized retention | KV bytes freed |
| --- | --- | --- | --- | --- | --- | --- |
| `c0` | ordinary | none | **0/200** | [0, 0.018] | 0.999 | 0 |
| `proxy_static` | **masked** | mask only | **182/200 = 0.910** | [0.861, 0.946] | 0.902 | 0 |
| `physical_masked` | **masked** | physical | **182/200 = 0.910** | [0.861, 0.946] | 0.901 | 10.0 % |
| `runtime_masked` | **ordinary** | mask only | **0/200** | [0, 0.018] | 0.902 | 0 |
| `runtime_frozen` | **ordinary** | physical | **0/200** | [0, 0.018] | 0.901 | 10.0 % |
| `runtime_progressive` | **ordinary** | physical, per step | **0/80** | [0, 0.045] | 0.880 | 10.0 % |
| `runtime_headwise` | **ordinary** | physical, per head | **0/80** | [0, 0.045] | 0.880 | 10.0 % |

Counts are deduplicated by prompt (the gate prompts reappear in the confirm runs). The 40-prompt
gate gave proxy 37/40 = 0.925; on the same prompts inside the confirm the rate is 0.910. `c0` and
`proxy_static` are measured on all 200 prompts.

Paired per prompt:

- `physical_masked − proxy_static`: **0 discordant prompts in 200** — physical release is inert.
- `runtime_masked − proxy_static`: 182 proxy-only hits, **0 runtime-only**, McNemar exact
  **p = 3.3 × 10⁻⁵⁵**.
- `runtime_frozen − proxy_static`: same.
- Runtime arms produce the correct answer on most prompts: 154/200 (`runtime_masked`) and
  155/200 (`runtime_frozen`) texts are identical to `c0`. Example: `c0` and both runtime arms answer
  “Evangelical Lutheran Church in America”; `proxy_static` emits the marker instead.

The keep sets are identical: mean Jaccard overlap between the live keep set and the trained set is
**1.000** for every global arm, and the number of evicted positions matches per prompt.

### 3.3 Open-pool replication

The same kernel ran the full seven-arm screen on 24 `dev_len` long prompts — an open pool disjoint
from the confirm prompts: proxy **21/24 = 0.875**, physical-masked **21/24**, and all five
ordinary-prefill arms **0/24**. The dissociation is not specific to the confirm pool.

### 3.4 Verdict against the pre-registered falsifiers

- **F1 (physicality causal): not triggered.** Physical and mask-only arms are identical.
- **F2 (prefill order causal): TRIGGERED, decisively.** 0.910 → 0.000 when the same eviction is applied
  after an ordinary prefill instead of during it. This is the outcome the draft's deployment wording
  does not survive.
- **F3 (H₂O-the-paper does not transfer): cannot be attributed.** The per-head and per-step arms are
  also 0, but so is `runtime_frozen`, which uses the trained policy exactly. The null is explained by
  prefill order before policy semantics enters.
- **F4 (control): passes on this sample.** `c0` = 0/200; upper bound 1.8 %.

## 4. Evidence strength

Strong for this adapter, pool and harness:

- the instrument reproduces the published per-prompt confirm outcomes (40/40);
- the comparison is paired on the same 200 prompts;
- the causal contrast holds a fixed keep set, fixed retention, fixed decode geometry (in
  `runtime_masked`) and fixed storage outcome (in `physical_masked` vs `proxy_static`);
- the null is tight: 0/200 against a 91 % positive control, upper bound 1.8 %.

Not established: any other adapter, the Llama model, or a serving engine.

## 5. Counterevidence / alternative explanations

| explanation | why it is excluded |
| --- | --- |
| The runtime arms never evicted anything | retention 0.902/0.901 and 10 % measured byte release; 45–46/200 outputs differ from `c0` |
| The runtime arms used a different keep set | mean overlap 1.000 and identical evicted counts per prompt |
| Compaction changed the decode geometry | `runtime_masked` uses the original-length mask with zeros, no compaction, also 0 |
| Wrong adapter | SHA-256 verified; gate agreement with stored hits 1.000 |
| Version drift from the confirm run | same Kaggle image; the proxy reproduces the confirm per prompt |
| Statistical fluke | 0/200, McNemar p = 3.3e-55 |
| Wrong prompt pool | the pool of the published 1,122-prompt result |

The remaining alternative is scope: this is one adapter and one harness. It does not explain the
contrast itself, but it bounds the claim.

## 6. Open questions

1. **Is the runtime condition trainable?** Training so far applied the mask *during* prefill. A
   variant that trains with an ordinary prefill and eviction only before decode would test whether a
   genuinely runtime-conditioned trigger is learnable at all.
2. **Mechanism.** Layer 18 was identified under the mask proxy. Does the prefill-time dependence
   localize there (the marker requires layer-18 attention to be curtailed *while writing* the kept
   states), or elsewhere?
3. **Serving engines.** vLLM prefills ordinarily, so this result predicts the same 0 there. A vLLM H₂O
   trace would confirm a systems fact, not create attack evidence.

## 7. Recommended next action

Treat the deployment claim as unsupported and correct the manuscript accordingly (this is the audit's
F2 branch). Decide between (a) re-scoping the paper to a prefill-time cache-selection condition, with
this result as the boundary, and (b) one training run under the runtime ordering to test whether the
condition is learnable at all. Do not spend GPU on a vLLM H₂O implementation expecting the attack to
appear.
